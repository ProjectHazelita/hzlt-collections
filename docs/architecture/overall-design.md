# hzlt!Collections 总体设计文档

Project Hazelita 项目 hzlt!Collections，简称 h!Cl。

本设计文档用于规划 h!Cl 的设计方向与迭代计划。该文档暂时先讨论前几个版本的开发目标。

## 项目概述

h!Cl 是一个适用于社群的开源、自托管优先、可扩展的内容分享平台。

用户可以在 h!Cl 注册和登录，在一个条目内发布文字、多张图片、图文混排的文章，并逐步支持音频、视频、链接、文件等。h!Cl 提供内容条目的组织、整理、检索、编辑、访问控制和内容治理。未来也可以引入 AI 作为可选增强组件，提供理解、审核和检索能力。

h!Cl 将会被用于公网、对外公开环境的 Hazelita 社群的 Hazelita Hub，和内网、仅局域网内使用的 101 Hub，因而 h!Cl 需要同时考虑二者的使用。

## 项目概念

### 核心对象

| 概念 | 定义 | 备注 |
| --- | --- | --- |
| Workspace / 空间 | 内容、成员、规则与配额的隔离边界 | 平台提供多个空间，不同空间之间互相隔离 |
| Entry / 条目 | 一个内容条目 | 内容条目可以是一段文字、一张或多张图片、图文混排的文章、音频、视频、链接、文件等 |
| Asset / 资产 | 被上传并存储的原始媒体、文件等内容 | 上传的内容原样保留一份存储 |
| Variant / 派生 | 缩略图、转码视频、编辑后的内容 | h!Cl 处理后的内容，与原始资产区分 |
| Collection / 合集 | 一个合集可以组织条目 | 例如，用户可以将多个内容放在同一个合集内 |
| Tag / 标签 | 人工选择的内容标签、创作者声明标签和自动生成的标签等 | 保留来源与置信度 |

以上概念描述平台的长期方向，不代表 v0.1 全部实现。v0.1 不提供 Workspace 功能，所有内容属于当前部署实例；暂不实现合集、自动标签等能力，具体范围见开发路线图。

### 用户功能

本节描述长期功能方向；v0.1 的交付范围以「v0.1 — First Atom」为准。

- 用户可以发布内容、编辑内容、选择内容的可见范围；也可以发布草稿。内容和草稿之间可以相互切换状态。
- 用户可以以瀑布流或网格形式浏览内容，查看条目的详情，下载条目的内容，按作者和时间等筛选内容。
- 用户可以为内容选定标签、加入合集、喜欢、收藏并搜索内容。「喜欢」与「收藏」是不同的功能。
- 用户可以使用 h!Cl 提供的图片编辑工具、部分 AI 扩展工具编辑内容。
- 用户可以举报、申诉内容。

## 总体架构

总体来说，采用模块化单体 + 独立后台 Worker。前端、API 和 Worker 使用 pnpm workspace 组织在同一个仓库中；API 与 Worker 分进程运行，共用需要的后端业务模块。

当前确定的技术栈如下：

| 部分 | 选择 | 说明 |
| --- | --- | --- |
| 前端基础 | React + TypeScript + Vite | v0.1 采用 SPA，不引入 SSR |
| 前端路由 | React Router | 条目详情具有可直接访问的独立 URL，站内可以弹窗呈现 |
| 服务端数据状态 | TanStack Query | 管理列表、详情、分页和操作后的数据更新 |
| 样式 | CSS Modules + CSS 自定义属性 | 沿用 Figma 设计变量，不引入另一套视觉规范 |
| 后端 | Node.js + TypeScript + Fastify | 使用受支持的 Node.js LTS 版本 |
| API 契约 | TypeBox + Fastify 类型提供器 + OpenAPI | 请求、响应校验、类型和接口文档基于同一套 schema |
| 数据库与数据访问 | PostgreSQL + Drizzle | 使用事务、约束和数据库迁移管理业务数据 |
| 后台任务 | pg-boss + 独立 Worker | 复用 PostgreSQL，不额外引入 Redis |
| 图片处理 | Sharp | 校验图片信息、生成缩略图等必要派生 |
| 身份认证 | 服务端 Session + Cookie；Argon2id | Session 保存在 PostgreSQL，密码只保存哈希 |
| 内容存储 | 本地文件存储 | 原始资产与派生文件分开保存 |
| 部署 | Docker Compose | 持久化 PostgreSQL 数据与本地资产目录 |

v0.1 不引入微服务、额外的构建编排平台或全局状态库。前端优先区分接口数据与组件局部状态，出现实际需要后再评估额外依赖。

音视频处理未来可以使用 FFmpeg；离线 AI 服务未来可以使用 Python + FastAPI / ONNX Runtime。FFmpeg、AI 服务、S3 适配器等不作为 v0.1 的运行依赖。SEO、SSR 和中文分词搜索暂不实现，也不部署独立搜索服务。

### 模块边界

业务 API 按身份、条目、资产、标签、喜欢、站点管理等实际业务划分，各模块通过显式服务接口交互。前端禁止直接操作数据库，也不依赖数据库表定义或后端实现。

可替换的外部能力在实际边界上通过 Provider 抽象，例如文件存储。v0.1 只实现本地存储 Provider，不预写 S3 实现，也不要求每个内部业务服务都套一层 Provider。

### API

采用版本化 REST + OpenAPI。TypeBox schema 同时用于请求、响应校验、类型推导与 OpenAPI 生成，避免重复维护多套接口定义。

API 层必须逐条检查操作权限，前端隐藏按钮不能代替后端授权。内容可见性、职员能力与审核状态分别判断，并覆盖条目、搜索、评论及媒体读取；不得通过猜测资产 ID 或旧媒体地址绕过限制。作者仍是唯一可编辑原文的人，职员只能按授权限制展示或删除。

对于 POST 创建与上传完成等接口，需要设计幂等键以抵御可能的重复提交。条目 ID 在 API 中以字符串传输，避免 JavaScript 大整数精度问题。

### 条目编号与链接

Entry ID 使用 PostgreSQL 的 `bigint identity` 自增整数，在当前部署实例内全局唯一。文字、图片以及未来其他类型的条目共用同一编号序列，不按作者或内容类型分别计数。

编号一经分配就保持不变，删除后不重排、不复用；编号可以有空缺，不能用最大 ID 代表条目总数。Entry ID 与图片等原始资产的 Asset ID 是不同的概念。

各类条目详情统一展示 `#编号`，同一条目在首页、喜欢、搜索、游客及手机端等上下文中保持同一编号。详情提供「复制条目链接」，复制当前站点的完整详情 URL，例如当前站点下 `/entries/1234` 对应的绝对地址，而不是只复制数字或原图 URL。仅在成功写入剪贴板后显示「链接已复制」。

条目链接必须支持直接打开和刷新，不依赖用户先进入瀑布流。自增 ID 不承担访问控制职责，未来的私有内容仍须通过授权保护。

### 上传与媒体处理

未完成校验、处理或可能的审核的内容始终位于私有临时区。服务端应当检查实际的文件格式、尺寸、大小等，不能只按后缀或 `Content-Type` 信任图片。

为过大的文件、嵌套解压、解析任务等设置资源和时间上限，处理程序不得越权；对象写入成功但数据库提交失败、任务中断、上传未完成等的情况，应当由定时回收与对账任务。

应用数据库保存资产的逻辑信息，而非直接存储大文件二进制。内容可以存储于本地，也可以在后续扩展到存储于 S3 存储等。

v0.1 的图片处理流程为：上传至私有临时区，完成实际格式、尺寸和大小校验，由 Worker 执行必要处理，成功后才允许作为资产发布。图片解码与派生处理必须限制资源，避免在 API 进程中执行不受限的解析任务。处理失败不得发布不完整资产，界面保留用户已填写的文字和标签，允许重新选择图片。

原图原样保留，缩略图等派生文件单独管理。v0.1 的「查看原图」在浏览器新标签页直接打开原始图片 URL，使用浏览器原生查看；站内大图查看器以后再实现。文件下载与查看原图是不同的操作。

### 身份与权限

站点归属与管理职责分离：

- 唯一所有者 `owner` 天然拥有全部能力，并独占职责任免与授权配置。
- 所有注册账号具有 `member` 基础身份，可独立承担 Administrator、Moderator，或同时承担两者。
- Admin 管理站点与用户；Mod 管理内容，二者不存在继承关系。Owner 在固定目录中配置各组权限，有效权限取兼任职责的并集。
- 未登录访客是访问状态，不是数据库角色。不提供任意角色、多级权限覆盖或单用户例外。

首个成功提交注册事务的用户成为 owner，后续为 member；事务锁与唯一索引防止并发产生多个 owner。职员权限在新请求中从数据库重新读取；封禁阻止登录并撤销会话。Admin 不能封禁其他职员或 Owner，所有人都不能封禁自己。

采用服务端 Session：Cookie 只携带不透明的会话标识，Session 保存在 PostgreSQL；密码使用 Argon2id 哈希。Cookie 使用 HttpOnly，并按部署环境配置 Secure、SameSite 等属性，配合 CSRF 防护。生产部署优先让前端与 API 同源，不把长期身份令牌放入 localStorage。退出登录应使对应的服务端会话失效。

条目保留五种受众范围。`content.restricted` 是越过受众限制的独立敏感能力，默认不授予 Mod；Owner 始终具备。职员管理内容不意味着可以查看隐藏邮箱或私密关注列表。

内容审核支持整条、标题、整块正文及逐个附件隐藏／恢复；不做句子级裁切或代写。普通 API 不返回隐藏原文，审核／作者编辑通过授权接口读取原文；隐藏媒体阻止普通访问。无剩余实质内容的条目不出现在正常列表，直接详情提供脱敏占位。作者编辑不自动恢复。永久删除独立授权并沿用附件清理流程。

用户资料限制同样不改写原始字段，统一作用于公开投影与头像媒体。管理操作和审计写入同一事务；审计保留操作者、目标、动作、原因与时间，不复制隐藏原文。设置按有效权限分组；sudo mode 与 2FA 留待后续实现。

## 开发路线图

该文档仅描述了，且我们目前只开发，h!Cl 的预览版本 v0.x。

开发的全流程名为 The Chlorine Cycle。当前版本先使用 `bumpp` 管理版本。

采用 Git Flow。遵守 Conventional Commit + 原子化 commit。一个 commit message 通常形如：

```text
<type>[optional scope]: <gitmoji> <description>

[optional body]

[optional footer(s)]
```

这里，`scope`、`body` 和 `footer(s)` 都是可选的，但通常建议包含 `body`。

分支按 Git Flow 管理：`main` 用于已发布的稳定版本，`develop` 用于开发集成；功能工作从 `develop` 创建 `feature/*`，完成后合并回 `develop`。需要准备发布时再创建 `release/*`，发布完成后合并到 `main`、标记版本标签，并将发布期间的修改合并回 `develop`。稳定版本的紧急修复使用 `hotfix/*`，修复发布后同样需同步回开发分支。分支按实际工作创建，不预建空分支。

用户原稿与后续修改分开提交，保持基线可追溯。当前仓库的首个原稿提交位于 `develop`；后续实现按上述分支约定推进。

### v0.1.0 — First Atom

完成一套可供社群实际使用的发布、浏览、互动与管理闭环。以下为发布时确认的实际范围，替代最初的单图最小范围。

#### 内容与发布

- 支持纯文字独立发布，或在同一条目组合最多 20 张图片、5 个文件和 5 个链接；标题可选，正文与附件至少有一项。
- 支持基础标签，以及所有内容类型的 NSFW／AI 声明。首页不显示普通标签；NSFW 预览模糊但属性徽章清晰，详情经确认后展示。
- 作者可在发布后编辑正文、标题、标签、声明、附件及可见范围；未保存离开前提示确认。
- 暂不实现独立草稿、富文本或图文混排编辑器。发布与编辑页面统一使用「发布条目」「编辑条目」，条目类型由实际附件类别区分。

#### 浏览与互动

- 主内容区只做瀑布流，暂不提供时间线或整齐网格切换。图片按原始宽高比展示，超长图允许例外处理；纯文字卡片直接展示正文摘要，长内容截断后在详情中完整阅读。
- 点击条目进入详情，提供独立条目链接、统一编号、复制条目链接和图片原图查看／下载。
- 支持喜欢与取消喜欢，每个用户对同一条目最多保留一次喜欢。详情显示数量与当前用户的喜欢状态，游客操作时引导登录；「喜欢」页面用瀑布流展示当前用户喜欢的内容。
- 基础搜索匹配正文、可选标题与标签，逻辑集中在后端。v0.1 不做中文分词或复杂检索，不部署独立搜索服务。
- 支持评论和回复，数据结构允许嵌套，前端最多展示一层缩进。作者可删除自己的评论或回复，确认后永久删除该评论及全部后代回复（包括其他作者的回复），保留同级评论。
- 每位用户拥有个人主页与作品瀑布流，支持关注／取消关注、粉丝人数及按隐私设置开放的关注／粉丝列表。「粉丝」右侧的「评论」页签按时间倒序分页展示该用户发表的评论与回复，仅返回访问者有权查看且未被整条隐藏的条目下的记录，所属条目标题与回复对象资料同样遵守审核限制。
- `GET /api/v1/users/:username/comments` 使用 `cursor`／`limit` 分页，返回评论、所属条目的编号与可展示标题以及 `nextCursor`；`DELETE /api/v1/entries/:id/comments/:commentId` 要求登录、CSRF 校验及评论作者身份，成功返回 204，删除与回复创建通过同一条目锁串行化。
- 删除 entry 不等同于审核隐藏：条目行保留并写入 `deletedAt`，评论、点赞及附件关联物理删除，附件资产标记为已删除并异步清理原文件与缩略图；保留的条目行不是可一键恢复的回收站。

#### 身份与管理

- 服务端 Session 登录，首位注册用户成为 owner；owner 可切换开放注册。
- 支持所有人、注册用户、作者粉丝、作者关注的人、仅作者五种条目可见范围；作者和 owner 拥有管理所需访问权限，媒体和评论遵循同一访问边界。
- 作者管理自己的条目，owner 可管理和删除全站内容但不能编辑他人正文；删除前确认，删除后撤销条目及关联媒体访问。
- Settings 包含个人资料、头像、个性签名、代词、邮箱、位置、最多五个社交链接、资料及关注列表公开设置和密码修改。owner 另有内容管理及站点标题、介绍、Logo 上传和注册开关设置。

#### 部署与设计依据

- 使用本地持久化存储与 Docker Compose，包含 API、Worker 和 PostgreSQL 等必要运行部分。
- 以 Figma「03 · Screens New」及共享组件为当前视觉依据，复用已有组件、设计 token 与图标，覆盖空状态、错误反馈和手机端布局。
- 原型预设样例不代替真实功能；注册、上传、媒体处理与下载、搜索、关注、权限和剪贴板均由实际应用流程提供。

#### 明确不纳入 v0.1.0

Workspace 功能及空间角色、合集、独立收藏功能、通知、富文本、独立草稿、图片编辑工具、独立全屏大图查看器、音视频、AI 服务、S3、自定义角色权限矩阵、SEO／SSR 与中文分词搜索。「AI 生成」等发布者手动声明不代表提供 AI 处理能力。
